层次

三层，判据是「谁拥有」

整个库不是按「文件类型」分层，而是按归属权分层。这条判据决定了几乎所有的操作约束：你拥有 raw/，我拥有 wiki/，两者之间是一条单向门。

一个自洽性检查：检索索引里的 506 篇，恰好等于四个内容目录之和（468 + 30 + 6 + 2）。templates/ 与 outputs/ 共 20 页被刻意排除在索引之外——它们不是知识，是脚手架和产物。

机制

证据链：每条结论都能钉回一个文件

这个库真正区别于「一堆笔记」的地方，是它有一条可反向检验的溯源链。链条本身不长，但四个环节各挂一个字段，任何一个字段丢了，链条就断。

四个字段，四条派生规则

  • 完整性 raw_sha256 ＋ last_verified：原始文件哈希对不上就报 SOURCE MODIFIED，须重新摄入并更新所有受影响页面。
  • 独立性 source_count 只数去重后的 raw 文件，不数来源页、不数章节。一本教材的十个章节在证据意义上不是互相独立的，逐节累加等于让一份材料给自己凑够三个来源。故大部头材料只对应一个来源页，页内用「已覆盖章节」表登记摄入范围。
  • 定级 1 个来源 → low；3+ → medium；5+ 且无重大矛盾 → 候选 high，须向用户展示证据列表并等一句确认才可写入。个人写作永不参与计数——不能用自己的文章给自己的认知背书。
  • 不覆盖 来源之间、以及同一份材料内部的矛盾，一律写进 Contradictions 节并列照录。两套口径若分属不同规范性文件、且材料未说明其效力关系，不得择一为准，只并列并提示「引用前核对原文」。

检索

检索后端，以及一条被实测否掉的路

检索用 qmd 2.8.3：索引落在 ~/.cache/qmd/index.sqlite，三个模型全部本地化（合计约 1.7 GB，检索时不需要联网）。这三个模型分属流水线的三个阶段——扩写、召回、精排——而本库只用到其中一个。

它有一个默认用法和一个实测可用的用法，默认用法在这台机器上慢到不可用。这就是本库自己写查询扩写、并且关掉重排的原因。下面两张图分别说的是「三个阶段里哪一段在跑」和「两条路差多少」。

一个反直觉的推论：「不加载」不等于「可以删」。另两个模型必须留在配置里——哪天不带 --no-rerank、或让 qmd 自己去扩写，它就会去加载它们，而那就是 19 分 47 秒的由来。

顺带回答「重建时去哪儿取件」：召回与精排两个模型就是 qmd 的原配，与官方默认 URI 同源同文件；只有扩写那个是替代品——qmd 原配的 qmd-query-expansion-1.7B 没有被 ModelScope 镜像，所以本库启用了它源码里被注释掉的旧默认（2026-10-10 已回源码逐字确认）。

命令加载的模型

换 embed 模型 ＝ 现有向量全部作废。每行向量除 model 外还带一个 fingerprint：hash(模型 URI ＋ 查询侧提示词 ＋ 文档侧提示词 ＋ 分块 token 数 ＋ 重叠 token 数)。所以换 embed 模型、或只是改一下分块参数，既有 5,259 块都会因指纹对不上而被判为过时，须整库重嵌——约 3 小时 25 分。这不是改一行配置的事。

降级链：三级，逐级更笨但更可靠

  • 一级 qmd query "vec: … lex: …" --no-rerank——向量 ＋ BM25 混合，本库的主力用法。
  • 二级 scripts/qmd-lite——仓库自带的纯 Python 标准库实现，只有 BM25、没有向量、没有重排，但零依赖、即时可用。它的命令形式与官方不同，不能照搬官方 flag。
  • 三级 直接读 wiki/index.md，人工从中挑 5 页。这是最后的兜底，不依赖任何工具。

三个配置点，都在同一个文件里

检索后端的可调项集中写在 ~/.config/qmd/index.yml，而它们分属三个不同的东西——这是排查检索问题的起点，也是唯一一处「误以为它在数据库里、其实不在」的地方。

配置点内容改了会怎样
collections.wiki.path 集合根路径，指向 …/tigger_vault/wiki 改错则检索整体失效。它不在数据库里，改完随便跑一条命令即自动同步
collections.wiki.context 四条语料结构说明，键 "" 为集合根，另有 concepts／sources／synthesis 三条 它是静态文本，会在每条检索结果头部原样回显，因此页数必然随摄入陈旧——本项目在文本里写死「页数为某日快照」
models 三个模型的本地绝对路径：embed＝Embeddinggemma 300M、generate＝Qwen3-0.6B、rerank＝Qwen3 Reranker 0.6B（均 Q8_0） 该节优先级高于环境变量，只设 QMD_EMBED_MODEL 无效。换模型须重连 ModelScope——本机访问不了 HuggingFace；⚠ 换 embed 另会作废全部向量

embed 的三个坑：极慢（495 篇实测 3 小时 25 分，纯 CPU）；默认有 30 分钟会话上限，必须加 --timeout 0；必须脱离终端运行。好消息是增量可续，中断后重跑只补未嵌的。另有一条并发禁忌：嵌入运行期间不要并行跑其他检索命令，它们会抢同一个 SQLite 的锁。

校验

十项检查，以及四类「不算错」的错

scripts/lint.py 跑十项检查：frontmatter 合法性、断链、索引一致性、空壳页、近重复命名、SHA-256 完整性、时效陈旧、跨语言重复、wikilink 格式、来源引用一致性。报告写进 wiki/outputs/，但它从不自动改页面。

这套检查最耐人寻味的部分，是它为「看起来像问题、其实不是」的情况留了一张裁定表。其中有四类形态，各有各的判据：

近重复命名检查的四种合法形态（均已裁定为误报，不再重复提议合并）
形态例子判据
对称的平行家族 vat-taxable-transaction／vat-deemed-…／vat-non-taxable-… 对称性——如实对应法律自身的结构，为迁就启发式检查而牺牲与领域术语的对应关系是本末倒置
枢纽页与专页 civil-law 与其 12 个专页 目录 vs 正文——父页只剩入口指针表，正文全部下沉。反向陷阱：父页若又开始自己写正文细则，就不再是枢纽页
词元包含而语义独立 co-ownership ⊃ ownership 子串包含 ≠ 语义重复——「共有」是「所有权」的一种特殊状态，不是它的上位或下位
命名缺陷
← 这一类要改，不记误报		 tax-service-professionals → tax-advisor 词序置换或单复数差异——两串词元集完全相同却语义不同，检索时必然拿错页；而改名取值优先取权威文件自己给出的英文名（Tax Advisor）

四类里只有第四类动手改。前三类的共同前提是「命名本身无误」——相似是因为领域结构本来就相似。这条区分很重要：一个启发式检查报出的警告，不等于一个需要修的问题；把前三类强行合并，代价是毁掉页面与法规结构之间的对应关系。

OCR 文本的四档措辞

教材是扫描件，OCR 必然有识别错误，数字和条款号尤其严重。本库的处置默认是「不臆断、不按比例推补」，并把不确定性写进页面而不是抹掉它。按证据强度分四档：

  • 可互证库内他处给出同一数字 → 写「数字已按库内互证校正」，并在 Contradictions 节写明互证依据与出处文件。
  • 字形可辨如「巧个工作日」→ 15 个工作日（字形关系可确证）→ 写「已按字形校正」，正文同时保留 OCR 原文。
  • 不可还原如罚款数额 OCR 作「10 佣元／5 元／2000 元／10 元」四种写法数位均有残缺 → 只录「两档、机构高于人员」这一结构，不推补。
  • 整段受损公开发布的政策用语句式可判 → 允许按通行表述补全，但必须照录残缺片段、显式标注「非互证非字形可辨」、写明全库已检索无第二处出处。

判据一句话：受损的是「一个数值」还是「一段可判句式」。前者只录结构，后者可补全但须留档。两条允许校正的实例都不是「因为不合理」或「按比例推」——一条靠字形，一条靠同段可对账的合计数。

依赖

库外的东西，以及改动会坏在哪

这个库有一半的生命在仓库之外：一个 Obsidian 配置目录、一个检索索引、一个 Python 虚拟环境。它们不在 raw/ 也不在 wiki/，但删掉任何一个，库都会残废一半。

两个「双层机制」的陷阱

  • 图谱隔离 graph-excluded: true 本身不生效。字段只是匹配依据，真正执行的是 .obsidian/graph.json 里那条搜索过滤器 -["graph-excluded":true]。所以新建系统文件时字段仍必须写，但看到图谱变乱时要先查过滤器在不在。
  • 节点显示名 Obsidian 原生图谱读的是文件名，不是 frontmatter 的 title。所以「slug 全英文、显示全中文」这对要求，靠的是 Front Matter Title 插件覆盖显示名——它永不重命名实际文件。插件没了，图谱就退回显示英文 slug。

这几处引用不在仓库里，因此不会被 git、搜索或一次 mv 照顾到。移动目录时按这张表核一遍：

改这里不改的后果
