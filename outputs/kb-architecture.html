01 总览 · 三层结构

权限边界决定了一切

这套系统的核心不是目录树，而是三个人为划定的边界：谁能写、谁只能读、什么绝不回流。

一处命名差异值得留意：Karpathy 原本划的第三层是 schema（规则层）——即 CLAUDE.md， 它把「通用聊天机器人」变成「守规矩的 wiki 维护员」。本库把 outputs/ 也并列为第三层。两者在本库中其实都在： CLAUDE.md 是 schema，outputs/ 是产物出口。

02 设计谱系 · Karpathy 的 llm-wiki

这套结构不是原创

2026 年 4 月，Andrej Karpathy 在 X 上公开了自己的个人知识库工作流，随后放出一份 gist——llm-wiki.md， 一份刻意写得抽象的「想法文件」：不是代码、不是产品，而是让人粘进 agent （Claude Code / Codex 等）自行实例化到自己的领域。本库的三层结构与操作契约都沿用它。

Obsidian 是 IDE，
LLM 是程序员，
Wiki 是代码库。—— Karpathy · llm-wiki gist

gist.github.com/karpathy/442a6bf555914893e9891c11519de94f  ·  X 帖 x.com/i/status/2039805659525644595

闭环：他 gist 里列的工具之一就是 qmd（本地 Markdown 混合检索：BM25 + 向量 + LLM 重排，Tobi Lütke 作）—— 本库的检索后端正是它。整条链路可上溯到这份 gist。

03 演化 · gist → 本库

沿用骨架，改掉不合身的地方

参照物是 Karpathy 的原始 gist，以及本机那份由它派生的《LLM Wiki 搭建教程》（30 页）。 gist 给的是通用模式，教程给的是通用模板；本库在实作中按实际语料改动了这些—— 骨架（raw 只读、wiki 全权、schema 即 CLAUDE.md、Confidence 门控）原样保留。

环节教程本库为什么改
操作集 3 条：Ingest / Query / Lint
（答案回填并入 Query）		 6 条：+ REFLECT
+ MERGE · + ADD-QUESTION		 教材与题库规模下需要跨来源合成、去重，以及一个待解答的问题队列
LINT 检查项 9 项 10 项 补「引用一致性」反向核对——页面存在、也登记了，但可能指错了书，断链与索引检查都看不见
QUERY 检索 qmd query 全量 自写 vec + lex
--no-rerank		 本机是无 GPU 虚拟机，全量一次 19 分 47 秒
raw/ 组织 按介质：articles / clippings / pdfs / notes 按内容类型：题库 / 公文 / 制度 / 代码表 / 教材 一份公文 PDF 属于公文而非 pdfs，只看路径判定会失准
来源计数 每份材料算一个来源 只数去重后的 raw 文件 否则一份材料能自己给自己凑够三个来源，置信度虚高
实体层收录 person / tool / institution / paper 只收机构 + 建库早期的法规 法规的内容已由概念专页承载，再建实体页只是第二个入口
近重复检测 Jaccard > 0.7 即报 另附一张已裁定误报表 平行命名家族（应税 / 视同应税 / 不属于应税）是法律自身的结构，不能为迁就启发式而合并
扫描件处理 无 新增 PDF / OCR 流程 教材是扫描件，且 OCR 文本必然有识别错误，须分档标注来源可靠性

有一处本库已经越过了他的前提。Karpathy 说在他的规模下（约 100 个来源、数百页），光靠 index.md 就够用， 不需要基于嵌入的 RAG 基础设施。本库已有 506 页 / 5,259 块——远过那条线， 因此必须上向量检索。这也解释了为什么本库的检索栈比 gist 描述的复杂得多。

04 raw/ 原始层

按内容类型归置的原始材料

这一层由人拥有。LLM 只能读取，不能修改、不能重命名、不能删除。

主维度 · 按内容类型

  • 题库/ — 28 份（CTA 必刷 550 题五科 · 岗位集中测试 23 条线）
  • 教材/text/ — 5 本 OCR 文本：税法一 · 税法二 · 涉税实务 · 涉税法律 · 财务与会计
  • 制度/ — 政策法规语料约 4,886 篇
  • 代码表/ · 公文/ · 个人写作/ — 各按用途备位

保留的介质类目录

  • clippings/ — 剪藏片段，含「一人公司涉税风险」专题 8 篇
  • pdfs/ · images/ · notes/ — 原始介质与随手笔记
判定以 frontmatter 的 type 为主、路径仅作兜底——同样一份公文 PDF 可能落在不同目录，只看路径会失准。

05 wiki/ 知识层

五类页面，各司其职

知识层由 LLM 全权读写。每个页面只承担一种角色，不混合。

目录角色是什么页数
sources/来源页一份原始材料 = 一页，是全部结论的唯一溯源依据29
concepts/概念页跨来源沉淀的认知单元，如「土地增值税清算」466
entities/实体页机构与建库早期的规范性文件6
synthesis/合成页REFLECT 产出的跨来源结论2
templates/模板页面骨架，不是内容页5

另有四个系统文件——index.md、log.md、overview.md、QUESTIONS.md， 以及 outputs/ 下的报告产物。它们全部带 graph-excluded: true， 由 Obsidian 图谱过滤器排除，不污染知识图谱。

06 规模 · 实测于 2026-10-12

这是一座概念密集型的库

页面构成决定了检索与维护的策略：概念多、来源少，是「深耕式」而非「广采式」的知识库。

466概念页
29来源页
506索引文件
5,259向量块
44.9 MB索引体积
16 : 1概念 / 来源

由此带来的结构特征

单一来源的概念页占比很高——按最近一次 LINT 与 Gap 报告，约 78% 的概念页 source_count = 1。这是本库最突出的结构性特征，也是每次摄入都在缓解的问题。

因此来源独立性被严格定义：source_count 只数去重后的 raw 文件—— 同一本书的不同章节不互相背书。

08 语义引擎

EmbeddingGemma 是什么

Google 2025 年 9 月开源的嵌入模型，主打端侧离线。它把一段文字压成一串坐标——语义相近的文字，坐标也相近。

版本EmbeddingGemma · 2025-09 发布
参数规模308M
输出维度768 维
上下文2,000 token
量化 / 体积Q8_0 · 318 MB（GGUF v3）
语言100+ 种，约 3,200 亿 token 训练

同一个模型，两套前缀

查询和文档要走不同的提示词格式——模型就是按这种格式训练的，前缀给错坐标就偏。

查询侧 → task: search result | query: …
文档侧 → title: … | text: …

这也是为什么换 embed 模型会导致全库向量作废——向量的指纹里就含这两个前缀的格式。

射程有限，且实测可验证。300M 是小模型，中文（非英语）能力相对弱：术语级表述能到 75–100%，别名（「土增税」）尚可， 但纯口语的迂回说法会失手——实测「卖房子赚的钱要被国家分走的那一块」三个候选分差只有 2 个百分点，等于在猜。 故自写扩写必须贴术语，不能往口语方向放飞。

09 检索流水线

两路召回，融合取前五

同一个问题同时走语义与字面两条路，各自返回一份排名，再用 RRF 合并。第三段的精排在本库被跳过。

10 三种检索范式

同一个问题，三种问法

实测于 2026-10-12，问的都是「房地产项目何时必须进行土地增值税清算」这件事。

命令机制查询形态结果耗时
qmd search 纯字面 · BM25 整句 无结果 0.48s
qmd search 纯字面 · BM25 关键词「土地增值税 清算」 命中 89% 0.55s
qmd vsearch 纯语义 · 向量 整句 命中 75% 22.8s 含冷加载
qmd query
--no-rerank		 vec + lex · RRF 自写 vec + lex 命中 100% 4.9s
检索回答问题 → 一律 qmd query 自写 vec + lex。 这是本库的检索主力。qmd search 不在检索链上。
验证索引 → search 与 vsearch 各一次。 「这个页面在不在索引里」本来就是字面问题，那里用字面匹配才对。

⚠ 三者的百分比不可互相比较——search 是 BM25 归一化分、vsearch 是余弦相似度、query 是融合分，口径不同。

11 降级链

后端失效时还有两级台阶

检索不是单点依赖。官方 qmd 不可用时逐级下退，每一级都能独立回答问题。

级后端能力代价
1 官方 qmd
当前生效		 BM25 字面 + 向量语义 + RRF 融合 需运行时与 3 个模型文件
2 scripts/qmd-lite
仓库自带		 仅 BM25（含中文单字 + 双字切分）无向量 零依赖、纯 Python 标准库、即时可用
3 wiki/index.md 人工浏览索引并挑选 无检索，靠人读
降级会丢掉什么：只有第 1 级有向量。一旦退到 qmd-lite， 全部「换个说法也能找到」的语义召回能力消失，只剩下字面命中。 这是两代后端最本质的差别。

13 操作契约

六条被写死的操作

所有对知识库的改动都必须走这六条之一。每条都有明确的触发词、步骤与产物——这是行为的唯一权威规范。

01

INGEST · 摄入

把 raw/ 的新材料转成来源页 + 概念页。11 步，含算哈希、概念名称对齐、逐一与用户确认要点。

02

QUERY · 查询

自写 vec + lex 检索 top 5，逐一读完再合成。每个结论必须溯源到来源页，不能只引概念页。

03

LINT · 健康检查

跑 10 项检查（断链、索引一致性、哈希完整性、引用一致性…），出报告但绝不自动改页面。

04

REFLECT · 综合分析

先反向搜寻反驳证据，再扫描跨来源模式，产出合成页与缺口报告。

05

MERGE · 合并

同语言与跨语言两套流程。必须先与用户确认，绝不自动执行，旧页留 redirect 不断链。

06

ADD-QUESTION · 记问题

把口语化疑问规范化成可回答的核心问题，追加到开放问题清单待日后来源解答。

14 质量机制

让错误无法静默存活

这套系统的可信度不来自「写得多」，而来自几条刻意设计的约束——其中多数源自 llm-wiki 模式本身。

① 不静默覆盖

来源之间的矛盾必须显式记入 Contradictions 节，不允许用新结论悄悄盖掉旧的。 同一份材料内部自相矛盾也照录，不擅自取舍。

② 来源独立性的粒度

source_count 只数去重后的 raw 文件——同一本书的不同章节不互相背书， 否则一份材料能自己给自己凑够三个来源，置信度就虚高了。

③ 置信度需人工确认

1 个来源 low、3+ medium 自动；到 5+ 且无重大矛盾时只是候选 high—— 须向用户展示定义与来源列表、得到明确确认才可设置。这是防「错误复利」的核心闸门。

④ 引用一致性反向核对

LINT 的第 10 项做「概念 → 来源」的反向核对：页面引用的来源，必须真的在其来源页登记过。 这是为了补上「页面存在但指错了书」这个断链与索引检查都看不见的洞。

最近一次完整 LINT（2026-10-08）：扫描 514 页，0 ERROR / 24 WARN / 72 INFO，WARN 与 INFO 全部为已裁定项。

15 收束

一条原则贯穿全部

raw/ 是唯一事实来源——知识层的每一个结论，都必须能溯源到其中的具体文件。 其余一切设计（只读边界、来源独立性、不静默覆盖、引用反向核对）都是这条原则的推论。
